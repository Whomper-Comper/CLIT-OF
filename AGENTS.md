# Agent guidance

This repository is the OpenFront Discord bot. The game and desktop control panel are separate projects; do not assume their code or toolchains are available here.

This checked-in guidance applies to any AI agent working locally or from GitHub. The [local agent handoff](docs/local-agent-guide.md) provides a portable workflow; use the current checkout as the authority.

## Start here

- Inspect the current working tree and preserve unrelated changes. Read [README.md](README.md) and [docs/development.md](docs/development.md); consult [docs/architecture.md](docs/architecture.md) before changing persistence, identity, roles, history, or background workers.
- Use the current repository and `package.json` as the authority for scripts and dependencies. The bot uses TypeScript with ESM/NodeNext and requires Node.js 22.13.0 or newer. Source imports use `.js` extensions; tests import compiled modules from `dist/`.
- Hosting target: Oracle Linux 9 ARM64 with 6 GB RAM by default. Use Node.js and its existing built-in SQLite driver; the user selected Node and stopped ANT compatibility work. See [Oracle ARM hosting](docs/oracle-arm.md). Earlier runtime experiments in [the SQLite assessment](docs/ant-sqlite.md) are historical evidence, not an active migration plan.
- Keep the README architecture disclaimer and [runtime/version compatibility matrix](docs/oracle-arm.md#version-and-architecture-compatibility) accurate: one bot codebase serves x86-64 and ARM64, but runtime binaries/native dependencies are architecture-specific. Distinguish Node's minimum API version, CI versions, the local benchmark runtime and the exact failed ANT probe; do not describe untested ANT/Oracle combinations as verified.
- Keep `.env`, credentials, identity tokens, runtime databases, backups, and other private files out of changes and output. Use an isolated database and test credentials for experiments.

## Implementation boundaries

- Follow existing command registration, access checks, private reply, validation, session-binding, and error-handling patterns. Update user-facing documentation when behavior changes.
- Multi-action command families use a required `action` choice, with legacy subcommand parsing for registration transition. The seven community/lobby families share `src/commands/actions.ts` for registration and delegate input checks to the lightweight `src/commands/action.ts` validator. Validate required/irrelevant inputs before replies, permissions, cooldowns or database work, using null-safe checks (`0` and `false` can be valid). Keep slash bounds/autocomplete in the definitions and use the real option resolver in legacy fixtures. Global and guild registrations are separate live actions.
- Preserve identity scope, deletion and unlink cleanup, role-write pacing, durable delivery/retry semantics, and bounded background work. Recheck current permissions and durable state after awaited external calls and immediately before side effects.
- Discord's single-role writes return updated member clones; do not assume the input role cache changed. Multi-clan and targeted sync sequences force-refresh just that member after a real write before the next clan, retaining live binding/config guards. A failed refresh must remain an error for later clans rather than advancing their successful-sync timestamps.
- Private statistics/configuration/community registries release expired entries during idle periods through `ExpiringSessions`; keep their ten-minute deadlines, caps, unreferenced timers and post-await revocation checks. Reads must not renew a menu. Community callers supply their own clock domain; preserve deterministic explicit-time behavior.
- API admission is per instance: eight active loaders, 64 queued, two-second queue deadline by default. Hold a slot through body handling/validation, assign freshness generations before admission, and retain per-caller defensive copies of cache-owned private loader results. Overload is a controlled retryable error, not permission to bypass the gate.
- A 429 starts an instance-wide OpenFront cooldown from `Retry-After` (30 seconds if unusable). Continue serving valid cache hits and check the cooldown before every transport attempt. The public ranked leaderboard is `/public/leaderboard/ranked`, pages 1 and 2. `/public/clan/{tag}` is date-bounded statistics, not a metadata or existence lookup.
- Keep transactions and composable savepoints synchronous; never hold one across an awaited external request. Batch work through existing store APIs while preserving identity/tombstone/revision checks, checkpoints, retry state, duplicate-input ordering, and rollback behavior.
- Clan save/removal queue preparation shares one mapping inventory and prepared statements inside the existing transaction; retain each member's obsolete roles, job versions, priority and creation time. History maintenance indexes improve scalar inventory/range reads at a measured write/storage cost; see the architecture performance evidence before adding redundant indexes.
- Bound list payload reads and decoding in the database query, preserving ordering, caps, draft filtering, and guild scope. Intersect effective-link inventories with fresh server membership; bot-wide links can belong to people outside the current server. See [efficient database work](docs/development.md#efficient-database-work).
- Coverage/weekly reports and history collection share `humanMemberLinks` in `src/memberLinks.ts`. It only filters supplied snapshots; keep fresh roster/link reads and post-await identity/configuration guards at the callers.
- Weekly player streams accept optional exact public-ID/Discord-ID pairs through one JSON parameter; an empty inventory must read no payloads. Canonical SQLite primary keys permit per-player counters, while cross-clan distinct totals still need game-ID deduplication. Complete iterators synchronously before awaiting.
- Make schema changes through the existing backed-up initialization and migration paths. Cover preservation of existing data, repeatable initialization, and failure behavior when relevant.
- Clan creation and edits validate the tag format and Discord settings locally. Existing clans autosave after fresh access and snapshot checks. Keep edit controls bound to the selected clan and retain the committed snapshot if Discord redraw fails. A new clan stays a draft until Create clan. Role mapping changes reconcile through the existing transaction; log and interval edits preserve the last sync timestamp and queued jobs.
- Keep Auto sync on the existing `/config → Clans` page. Require the config role for provisioning and paced writes, and check the live session again after awaits. New mappings use a fresh role with no added permissions. Verify new tags with the public existence endpoint and use current server links and player profiles for membership. Never infer Discord identity from names or adopt an unconfigured role by name.
- Keep clan configuration snapshots in explicit field order: legacy migrations append columns, so database row property order can differ from a new draft. Unsaved menu drafts publish after a successful redraw.
- Keep external requests and runtime side effects out of local tests. The lobby codec is pinned to an upstream revision; see [lobby feed operations](docs/operations.md#lobby-feed-operations) before changing it.
- Lobby count frames may reuse only privately owned normalized state; keep defensive `snapshot()`/`getLobby()` results, duplicate-ID behavior and all freshness/invalidation checks. The due index includes `(status,next,updated,id)`; initialization upgrades the recognized legacy definition once and preserves custom indexes and saved notifications.
- Elo drawing optimizations must preserve decoded pixels and all observations used for scales/labels. Ordered Bresenham endpoints cannot be freely reversed, and marker `round(center + offset)` can differ from `round(center) + offset` at floating-point boundaries. Keep the original marker arithmetic; avoid deduplication allocations for sparse plots.

## Verification and operations

- Run `npm run build` before targeted `node --test` runs so tests do not use stale `dist/`. Run `npm test` for changes spanning subsystems or before handing off a completed code change. See [docs/development.md](docs/development.md) for targeted suites and Windows sandbox limitations.
- Test observable behavior and relevant failure, permission, and post-await race paths. Pair operation counts or query plans with those behavioral checks for performance changes; avoid machine-dependent timing assertions.
- `npm start`, `npm run dev`, command registration, PM2 commands, and `npm run update` can affect live services. Treat them as deliberate operational actions, not local verification. Do not claim local tests prove a live deployment or external API works.
- GitHub Oracle deployment is manual-only (`workflow_dispatch` in `.github/workflows/deploy.yml`); pushes to `main` run architecture verification without deploying. Keep publication and deployment separate; do not restore automatic deployment triggers without explicit authorization.
- Report the checks actually run and any failures or limitations. Do not reset unrelated work or force-push.
- Verified integrated gate (6 November 2026): Node 26.4.0 Windows x64 passes all 891 cases outside the sandbox after combining main's newer infrastructure with the command/report/member-filter refactors. Preserve legacy request support, per-action input checks and registration bounds; local verification does not register or deploy commands.
- `node tools/check-runtime.mjs` is a credential-free local capability probe, including the SQLite iterator required by history readers; `node --expose-gc tools/benchmark-bot.mjs` measures an offline in-memory weekly workload after build. Linux x64/ARM64 verification on main/feature pushes is separate from deployment. Report runtime/architecture with measurements; do not equate Windows results with Oracle ARM performance.
- Before publishing, review the exact staged diff and include updated shared guidance and documentation. Keep published handoffs portable; exclude machine-specific paths, credentials, runtime data, and unrelated local work. Report the committed revision and whether its push succeeded.
